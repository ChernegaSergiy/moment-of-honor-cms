# RFC 0001 — Moment of Honor CMS

**Статус:** Draft
**Автор:** CSSM Group
**Дата:** 2026-08-15
**Проєкт:** Moment of Honor
**Пов'язаний застосунок:** «Хвилина мовчання»

## 1. Коротко

Цей RFC пропонує створення **Moment of Honor CMS** — системи керування контентом для застосунку «Хвилина мовчання», побудованої на базі GitHub.

GitHub використовується як сховище контенту, систему версіонування та механізм керування доступом. **GitHub App** надає авторам інтерфейс для роботи з контентом через GitHub API.

Для взаємодії між клієнтом та GitHub використовується serverless API, а застосунок отримує готовий **JSON Feed**.

Основна мета архітектури — створити незалежний канал доставки контенту, не роблячи Instagram API або scraping Instagram залежністю десктопного застосунку.

---

# 2. Мотивація

У застосунку «Хвилина мовчання» планується вкладка **«Головна»**, яка міститиме стрічку інформаційних матеріалів.

Одним із можливих джерел контенту розглядався Instagram громадської організації «Вшануй».

Безпосередня інтеграція Instagram із клієнтом має суттєві недоліки:

* необхідні можливості Instagram API можуть вимагати App Review;
* клієнт не повинен безпосередньо взаємодіяти з Instagram API;
* API та політики сторонньої платформи можуть змінитися;
* scraping не гарантує стабільної структури даних;
* Instagram не є контрольованим сховищем контенту для застосунку.

Тому контент пропонується зберігати у власному джерелі:

```text
Автори
   │
   ▼
Moment of Honor CMS
   │
   ▼
GitHub Repository
   │
   ▼
JSON Feed
   │
   ▼
«Хвилина мовчання»
```

Instagram при цьому може залишатися окремим каналом публікації, але не є необхідною частиною роботи застосунку.

---

# 3. Цілі

Moment of Honor CMS повинна:

* дозволяти авторизованим користувачам створювати та редагувати контент;
* підтримувати дописи та stories;
* зберігати текстовий контент у GitHub;
* зберігати пов'язані медіафайли;
* використовувати Git для історії змін;
* підтримувати декількох авторів;
* використовувати GitHub для автентифікації та авторизації;
* надавати застосунку готовий JSON Feed;
* не вимагати від клієнта доступу до GitHub API;
* не вимагати від клієнта доступу до Instagram API;
* працювати без власного постійно запущеного сервера;
* дозволяти автоматизовану обробку контенту через GitHub Actions;
* зберігати останню доступну версію feed на стороні клієнта.

---

# 4. Нецілі

Moment of Honor CMS не ставить за мету бути універсальною CMS або соціальною мережею.

Система не повинна копіювати функціональність Instagram, реалізовувати соціальні взаємодії, коментарі, лайки чи інші функції, які не потрібні для доставки інформаційного контенту в «Хвилину мовчання».

---

# 5. Загальна архітектура

Система складається з чотирьох основних компонентів:

```text
                         ┌──────────────────┐
                         │     Автори       │
                         └────────┬─────────┘
                                  │
                           GitHub authorization
                                  │
                                  ▼
                         ┌──────────────────┐
                         │   GitHub App     │
                         │                  │
                         │ Moment of Honor  │
                         └────────┬─────────┘
                                  │
                             GitHub API
                                  │
                                  ▼
                  ┌────────────────────────────┐
                  │      GitHub Repository     │
                  │                            │
                  │  content/                  │
                  │  media/                    │
                  │  feed.json                 │
                  └────────────┬───────────────┘
                               │
                         generated feed
                               │
                               ▼
                  ┌────────────────────────────┐
                  │     Serverless API         │
                  │                            │
                  │     JSON Feed / Cache      │
                  └────────────┬───────────────┘
                               │
                               ▼
                  ┌────────────────────────────┐
                  │    «Хвилина мовчання»      │
                  └────────────────────────────┘
```

---

# 6. GitHub Repository

Repository є основним сховищем контенту.

Приблизна структура:

```text
moment-of-honor-content/
│
├── content/
│   ├── posts/
│   │   ├── 2026-08-15-example.json
│   │   └── ...
│   │
│   └── stories/
│       ├── 2026-08-15-01.json
│       └── ...
│
├── media/
│   ├── posts/
│   └── stories/
│
├── feed.json
│
└── schema/
    └── content.schema.json
```

GitHub таким чином одночасно виконує функції:

* content storage;
* version control;
* audit log;
* backup;
* access control;
* API для роботи з контентом.

Repository може бути приватним.

---

# 7. Формат контенту

Допис описується окремим JSON-документом.

```json
{
  "id": "2026-08-15-example",
  "type": "post",
  "title": "Пам'ятаємо",
  "content": "Текст допису...",
  "media": [
    "media/posts/2026-08-15-example.jpg"
  ],
  "author": "moment_of_honor",
  "publishedAt": "2026-08-15T10:00:00Z"
}
```

Story:

```json
{
  "id": "2026-08-15-01",
  "type": "story",
  "media": [
    "media/stories/2026-08-15-01.jpg"
  ],
  "publishedAt": "2026-08-15T12:00:00Z",
  "expiresAt": "2026-08-16T12:00:00Z"
}
```

Точна схема контенту визначається окремою JSON Schema.

---

# 8. GitHub App

**Moment of Honor GitHub App** є точкою авторизації та доступу до repository.

Автор проходить автентифікацію через GitHub, після чого CMS визначає доступ користувача до відповідного repository.

GitHub App використовує GitHub API для:

* створення файлів;
* редагування файлів;
* видалення файлів;
* завантаження медіа;
* отримання стану repository;
* створення commit;
* отримання metadata про зміни.

GitHub App повинна мати лише необхідні permissions.

Основним permission є:

```text
Repository permissions
└── Contents: Read & write
```

Додаткові permissions надаються лише для функцій, які їх безпосередньо потребують.

---

# 9. Авторизація

Окрема система користувачів не створюється.

Ідентичність автора визначається GitHub account.

```text
Author
   │
   ▼
GitHub
   │
   ▼
GitHub App
   │
   ▼
Repository access
```

Права доступу до контенту контролюються через installation GitHub App та permissions repository.

---

# 10. CMS API

Між клієнтськими інтерфейсами CMS та GitHub API використовується serverless API.

Його завдання — не замінити GitHub як backend, а надати контрольований шар над GitHub API.

Приблизні endpoints:

```http
GET  /auth/github
GET  /auth/github/callback

GET  /api/posts
POST /api/posts
GET  /api/posts/:id
PUT  /api/posts/:id
DELETE /api/posts/:id

GET  /api/stories
POST /api/stories
PUT  /api/stories/:id
DELETE /api/stories/:id

POST /api/media
POST /webhook/github

GET /feed.json
```

Конкретний API може бути скорочений або розширений залежно від реалізації CMS.

---

# 11. JSON Feed

Десктопний застосунок не працює безпосередньо з GitHub.

Він отримує готовий feed:

```http
GET /feed.json
```

Наприклад:

```json
{
  "version": 1,
  "generatedAt": "2026-08-15T12:00:00Z",
  "posts": [],
  "stories": []
}
```

Таким чином клієнт не знає:

* де зберігається repository;
* як працює GitHub App;
* хто має доступ до repository;
* як створюються commits;
* як генерується контент;
* чи використовується Instagram.

Для клієнта існує лише read-only feed.

---

# 12. Генерація Feed

Feed не повинен формуватися шляхом звернення до GitHub API під час кожного запиту клієнта.

Після зміни контенту feed генерується або оновлюється автоматично.

```text
GitHub Repository
       │
       │ change
       ▼
GitHub Actions / Worker
       │
       ├── validate
       ├── process media
       └── generate feed
                    │
                    ▼
                feed.json
```

Це зменшує кількість запитів до GitHub API та дозволяє кешувати готовий результат.

---

# 13. GitHub Actions

GitHub Actions використовується для автоматизації операцій, пов'язаних із repository.

Можливі операції:

* перевірка JSON Schema;
* перевірка структури контенту;
* генерація `feed.json`;
* оптимізація зображень;
* перевірка медіафайлів;
* публікація feed;
* інші автоматизовані операції після commit.

Таким чином частина backend-логіки може виконуватися без окремої серверної інфраструктури.

---

# 14. Webhooks

GitHub App отримує webhook-и про зміни repository.

```text
GitHub
   │
   │ webhook
   ▼
Serverless API
   │
   ├── verify signature
   ├── process event
   └── update feed/cache
```

Webhook-и використовуються для реакції на зміни контенту, а не для безпосереднього обслуговування клієнтів.

---

# 15. Serverless Infrastructure

Власний VPS або постійно працюючий сервер не потрібен.

Serverless API може бути реалізований, наприклад, через Cloudflare Workers.

```text
                   Cloudflare
                       │
                       ▼
                ┌──────────────┐
                │    Worker    │
                └──────┬───────┘
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        GitHub API          JSON Feed
```

Worker виконує роль адаптера між GitHub та CMS і відповідає за authentication, authorization, validation, webhook-и та кешування.

---

# 16. Кешування

`feed.json` повинен кешуватися на edge-рівні.

```text
                  feed.json
                     │
              Cloudflare Cache
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
    Client 1      Client 2      Client N
```

Кількість клієнтів не повинна пропорційно збільшувати кількість запитів до GitHub API.

---

# 17. Робота без мережі

«Хвилина мовчання» повинна зберігати останній успішно отриманий feed.

Якщо feed тимчасово недоступний:

```text
Network request
      │
      ├── success ──► update cache
      │
      └── failure ──► use cached feed
```

Недоступність стрічки не повинна впливати на основну функціональність застосунку.

---

# 18. Instagram

Instagram не є backend Moment of Honor CMS.

Система не повинна залежати від можливості:

* отримувати Instagram stories;
* отримувати Instagram posts;
* отримувати Instagram media;
* парсити Instagram;
* виконувати Instagram API requests із клієнта.

У майбутньому Instagram може бути інтегрований як додатковий канал:

```text
                 Moment of Honor CMS
                    /          \
                   /            \
                  ▼              ▼
        «Хвилина мовчання»    Instagram
```

При цьому джерелом істини залишається CMS.

---

# 19. Медіафайли

Зображення та інші медіафайли зберігаються окремо від JSON metadata:

```text
media/
├── posts/
│   ├── abc.jpg
│   └── def.jpg
│
└── stories/
    ├── 001.jpg
    └── 002.jpg
```

Metadata містить посилання на відповідний файл.

Це дозволяє незалежно обробляти текст та медіа.

---

# 20. Git як історія контенту

Кожна зміна контенту створює Git commit.

Наприклад:

```text
Create post: Пам'ятаємо Сергія
Add media: photo-001.jpg
Update post: Пам'ятаємо Сергія
```

Git автоматично забезпечує:

* історію змін;
* можливість перегляду diff;
* rollback;
* attribution;
* audit trail.

CMS не повинна реалізовувати окремий журнал змін.

---

# 21. Безпека

Система повинна:

* використовувати мінімальні GitHub App permissions;
* перевіряти підписи GitHub webhook;
* не передавати GitHub credentials клієнту;
* не зберігати installation access tokens довше, ніж необхідно;
* обмежувати доступ GitHub App конкретними repositories;
* застосовувати rate limiting до CMS API;
* відокремлювати read-only feed від адміністративного API;
* не дозволяти клієнту безпосередньо змінювати repository.

---

# 22. Надійність

Основна функціональність застосунку не повинна залежати від доступності CMS.

Критична функція:

```text
09:00
  │
  ▼
«Хвилина мовчання»
  │
  └── не залежить від CMS
```

Стрічка є додатковою функціональністю.

Тому проблеми з GitHub, Cloudflare, API або мережею не повинні перешкоджати проведенню хвилини мовчання.

---

# 23. Переваги архітектури

### GitHub як infrastructure

Не потрібно створювати окремі:

* database;
* object storage;
* authentication system;
* version control;
* audit log.

### GitHub App як контрольований доступ

Автори працюють із CMS, а не отримують прямий доступ до внутрішньої архітектури застосунку.

### Serverless

Не потрібен власний VPS або постійно запущений backend.

### Статичний Feed

Основна кількість клієнтських запитів може обслуговуватися кешем.

### Незалежність від Instagram

Зміна API Instagram або повна відмова від його використання не ламає Moment of Honor.

---

# 24. Недоліки та обмеження

GitHub не є спеціалізованою базою даних або media storage.

Потенційні обмеження:

* Git repository не оптимальний для великої кількості великих медіафайлів;
* GitHub API має rate limits;
* великі файли збільшують розмір repository;
* Git commit не є повноцінною транзакційною системою;
* складний CMS workflow може зробити GitHub-based architecture надмірно складною;
* система має залежність від GitHub infrastructure.

Ця архітектура тому орієнтована на контрольований інформаційний контент Moment of Honor, а не на масштаб соціальної мережі.

---

# 25. Висновок

Moment of Honor CMS пропонується будувати за принципом:

> **GitHub зберігає контент, GitHub App керує доступом, serverless API ізолює GitHub від клієнта, а «Хвилина мовчання» споживає готовий JSON Feed.**

Повна схема:

```text
                         ┌──────────────────┐
                         │     Автори       │
                         └────────┬─────────┘
                                  │
                             GitHub OAuth
                                  │
                                  ▼
                         ┌──────────────────┐
                         │   GitHub App     │
                         └────────┬─────────┘
                                  │
                             GitHub API
                                  │
                                  ▼
                  ┌────────────────────────────┐
                  │      GitHub Repository     │
                  │                            │
                  │  Content + Media + Git     │
                  └────────────┬───────────────┘
                               │
                     Webhook / GitHub Actions
                               │
                               ▼
                  ┌────────────────────────────┐
                  │    Serverless API          │
                  │                            │
                  │ Auth / API / Feed / Cache  │
                  └────────────┬───────────────┘
                               │
                         HTTPS / JSON
                               │
                               ▼
                  ┌────────────────────────────┐
                  │    «Хвилина мовчання»      │
                  │                            │
                  │  Головна → Feed            │
                  └────────────────────────────┘
```

**Жодного етапування в архітектурі не передбачається:** це цілісна модель системи, а не план її поступової реалізації.
